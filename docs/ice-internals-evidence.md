## 1. Overview and architecture

Ice is an agent app (`LSUIElement`, no Dock icon) that manages the macOS menu bar with three NSStatusItems of its own, which the source calls control items. It hides other apps' items by stretching a control item until every item to its left lands past the edge of the display.

Two processes do the work:

| Component | Bundle path | Role |
|---|---|---|
| Main app | `Contents/MacOS/Ice` | Control items, section state, Ice Bar panel, item enumeration, image capture, synthesized mouse events, hotkeys, rehide logic |
| XPC service | `Contents/XPCServices/MenuBarItemService.xpc` | One job: on macOS 26, map each status item window to the PID of the app that created it, using Accessibility |
| Sparkle 2.8.0 | `Contents/Frameworks/Sparkle.framework` | Updates. **Inferred:** not part of hide/show or the Ice Bar |

The XPC service exists because on macOS 26 Control Center owns every status item window, so the window owner PID no longer names the app behind an item. Resolving the real app takes Accessibility calls, which block the calling thread; the source comment gives that as the reason for running them out of process.

Launch sequence from source:

1. `applicationWillFinishLaunching` runs defaults migrations.
2. `applicationDidFinishLaunching` hides Ice's own main-menu items, sets the private connection property `SetsCursorInBackground`, then branches on permissions.
3. `setupTask` stops permission polling, then sets up settings, `MenuBarManager` (control items and sections), the XPC connection (macOS 26 only), appearance, `EventManager` (input monitors), `MenuBarItemManager` (first item cache) and the image cache.

## 2. Section model and hiding via control items

### 2.1 How it works

Ice splits the menu bar into three sections, ordered right to left: visible, hidden and always-hidden. Each section owns one NSStatusItem:

- **Visible control item**: the Ice icon. Its length stays at `NSStatusItem.variableLength` (-1).
- **Hidden and always-hidden control items**: invisible dividers that mark section boundaries.

AppKit lays status items out from the right edge of the menu bar toward the left. To hide a section, Ice sets that section's divider length to 10,000 pt. Every item ordered to the left of the divider moves past the left edge of its display and stops being drawn, while its window keeps existing. To show the section, Ice sets the length back to variableLength. In the default "no divider" style it then collapses the divider to zero visible width: it deactivates one AppKit layout constraint, sets length 0 and shrinks the window to 1 pt. The divider stays in the menu bar because Ice computes section membership from the dividers' x positions.

State transitions:

| Action | Icon (visible item) | Hidden divider | Always-hidden divider |
|---|---|---|---|
| `show(visible)` or `show(hidden)` | showSection | showSection | unchanged |
| `show(alwaysHidden)` | showSection | showSection | showSection |
| `hide(visible)`, `hide(hidden)`, or any hide while the Ice Bar is in use | hideSection | hideSection | hideSection |
| `hide(alwaysHidden)` | unchanged | unchanged | hideSection |
| Cmd-drag inside the menu bar with ShowAllSectionsOnUserDrag on | showSection | showSection | showSection (no rehide checks start) |

Length and appearance per state:

| Item | showSection | hideSection |
|---|---|---|
| Visible (icon) | -1 (variableLength), image `iceIcon.visible` | -1, image `iceIcon.hidden` |
| Divider, noDivider style (default) | constraint inactive, length 0 (3 while Cmd-dragging), window width 1 (3 while dragging), title `\|` while dragging | constraint active, length 10,000, `appearsDisabled` true |
| Divider, chevron style | length -1, template chevron image | length 10,000 |

Ordering and persistence: AppKit stores each status item's position in the app's standard UserDefaults under `NSStatusItem Preferred Position <autosaveName>`. Before creating each item, Ice seeds that key (0 for the icon, 1 for the hidden divider) so its items start to the right of existing items. It also seeds `NSStatusItem Visible <autosaveName>` = true and, on macOS 26 only, `NSStatusItem VisibleCC <autosaveName>` = true. Per the source comments, setting `isVisible = false` or calling `removeStatusItem` deletes the stored position, so Ice reads it first and writes it back afterward.

## 3. Discovering items and their owning apps

### 3.1 How it works

Ice reads the menu bar from the window server, mostly through private CGS calls:

1. `CGSGetWindowCount(main, 0)` sizes a buffer.
2. `CGSGetProcessMenuBarWindowList(main, 0, count, buf, &n)` returns every menu bar window of every process, including the Window Server "Menubar" backdrop windows at level 24.
3. Optional filters: **itemsOnly** (`CGSGetWindowLevel` is not 24), **activeSpace** (`CGSCopySpacesForWindows` with mask 7 contains `CGSGetActiveSpace`), **onScreen** (the ID is in `CGSGetOnScreenWindowList`).
4. Ice reverses the list to get left-to-right order.
5. Metadata comes from the public `CGWindowListCreateDescriptionFromArray`, fed a CFArray of raw window IDs.
6. Live geometry comes from `CGSGetScreenRectForWindow`, with `kCGWindowBounds` as the fallback.

An item's identity is a tag of (namespace, title). The title is `kCGWindowName`: the NSStatusItem autosave name, or `Item-N` when the app set none. Before macOS 26 the namespace is the owning app's bundle ID. On macOS 26 the owner is always Control Center, so Ice sends each window to the XPC service, which finds the creating app through Accessibility:

1. Require `AXIsProcessTrusted`.
2. Wait for stable bounds: up to 5 reads of `CGSGetScreenRectForWindow`, sleeping 10, 20, 30, 40, 50 ms between reads. Give up if they never settle.
3. Walk running apps (apps with a known extras bar first). Read each app's `AXExtrasMenuBar` children, skip disabled children, and take the first child whose `AXFrame` center lies within 1 pt of the window's center.
4. Cache window ID to PID.

## 4. Moving and clicking items (synthesized events)

### 4.1 How it works

Ice moves and clicks other apps' items with synthesized CGEvents. It uses no AX press actions and posts no drag events.

**Move**: a Command-modified `leftMouseDown` at the edge of the target item, then a plain `leftMouseUp` sent twice at the drop point. Both come from a cached HID-state event source. Each event carries integer fields: field 42 (`eventSourceUserData`) holds a unique tag (the event object's own address), fields 91 and 92 hold the item window ID, and the undocumented field 51 (0x33) also holds the window ID, on move events only. The mouse-up carries the destination target item's window ID.

**Delivery relay** (`scrombleEvent`, labeled in source as "Casts forbidden magic"): two null events serve as entry and exit markers. An active head-insert tap sits on the item's source PID, and a listen-only tail tap sits at the session tap. Ice posts the entry marker to the PID. The PID tap swallows it and posts the real event to the session tap. The session tap sees the real event and re-posts it to the PID. The PID tap lets the real event through to the app, then emits the next entry marker or the exit marker. The exit marker ends the relay.

**Click** (`postEventWithBarrier`): the same two taps, except the PID tap listens to null events only and the real event is never re-posted to the PID. Click events set `mouseEventClickState` to 1 on down and 0 on up.

**Around every operation**: hide the cursor, save its position, stop Ice's own input monitors, wait until the user pauses input, then warp the cursor back and show it. A move succeeds when polling `CGSGetScreenRectForWindow` shows the item's origin change after the down, and again after the up. Timeouts adapt per item.

**Temporary show**: the dividers stay expanded. Ice drags the one off-screen item into the visible section, left of the first visible item that leaves room past the app menu and notch, clicks it, records any new window its app opens, and after 15 s drags it back.

## 5. Ice Bar

### 5.1 How it works

The Ice Bar is a single long-lived `NSPanel` subclass (`IceBarPanel`) that `MenuBarManager` creates once. It is borderless and non-activating, sits at window level 25 (mainMenu + 1), has no window shadow and no animation, and appears through `orderFrontRegardless`. It never becomes key and never activates Ice.

With UseIceBar on, showing a section leaves both dividers expanded at 10,000 pt, so hidden items stay off-screen. Only the Ice icon switches to its "shown" image. Ice refreshes its item and image caches (1 s cap), builds a new SwiftUI hosting view, positions the panel under the menu bar, samples the background color, and orders the panel front.

Item images come from the deprecated `CGWindowListCreateImageFromArray`, which captures windows by ID from their window server backing stores, so items parked at negative x can still render. Ice captures one composite of all the section's item windows and crops each item out. Excluded or transparent items get a second, per-window capture.

Clicking an image first hides the section, which closes the bar. After 25 ms Ice clicks the real item if its window is on screen, or temporarily shows it (section 4).

## 6. Triggers, hotkeys and rehide

### 6.1 How it works

Input capture uses two mechanisms:

- **NSEvent "universal" monitors**: a local plus a global monitor with the same mask. Four exist: left and right mouse down, left mouse up, left mouse dragged, scroll wheel.
- **One persistent CGEventTap**: listen-only, mouse-moved only, at the HID tap, tail-append. Used for show-on-hover. (Move and click create short-lived active taps, section 4.)

"Empty menu bar space" is a four-part test: pointer inside the menu bar rectangle, outside the app menus, outside every item window, outside the notch.

Global hotkeys use Carbon `RegisterEventHotKey`. They ship unassigned.

Auto-rehide (default on) has three strategies: **smart** (default; a click into a regular active app or the Dock, checked 250 ms later), **timed** (a 15 s one-shot timer once the pointer leaves the menu bar), and **focusedApp** (frontmost-app change, then 0.1 s).

## 7. Permissions

### 7.1 How it works

Ice models two permissions. **Accessibility** is required: without it, setup never runs, so no monitors, taps or hotkeys exist. **Screen Recording** is optional: without it, Ice runs in "Limited Mode", where the Ice Bar and the layout pane show a "requires screen recording" message and no item images are captured. Ice calls no Input Monitoring API.

Ice detects Screen Recording by reading `kCGWindowName` of another app's menu bar item window: a readable title means granted. It falls back to `CGPreflightScreenCaptureAccess`. It requests the permission through `SCShareableContent` on macOS 15 and later.

### 10.2 Private APIs the port cannot avoid (inferred)

- None for the bare hide/show core: public NSStatusItem plus undocumented defaults keys suffice.
- For the Ice Bar on macOS 26: reliable per-space filtering of item windows (`CGSCopySpacesForWindows`, `CGSGetActiveSpace`) and the active menu bar display (`CGSCopyActiveMenuBarDisplayIdentifier`), unless a public rule for discarding per-display copies proves stable.
- `CGWindowListCreateImageFromArray` is public but deprecated; the Swift overlay hides it, the C symbol remains.
- Field 0x33 is an undocumented value passed through a public function.

### 10.3 Candidate Rust crates

objc2, objc2-foundation, objc2-app-kit (NSStatusBar, NSPanel, NSEvent, NSWorkspace), objc2-core-graphics or core-graphics plus core-foundation (CGEvent, CGWindowList), objc2-application-services or accessibility-sys (AX), objc2-screen-capture-kit (permission prompt), block2 (NSEvent monitor blocks), dispatch2 (main-queue hops). Declare CGS functions and `CGWindowListCreateImageFromArray` in `extern "C"` blocks linked against the CoreGraphics framework. Check each crate's current version before use.

Signatures from Shared/Bridging/Shims.swift, in C terms: `CGSGetProcessMenuBarWindowList(int32 cid, int32 target, int32 count, uint32 *list, int32 *outCount) -> CGError`; `CGSGetScreenRectForWindow(int32 cid, uint32 wid, CGRect *out) -> CGError`; `CGSGetWindowLevel(int32 cid, uint32 wid, int32 *out) -> CGError`; `CGSCopySpacesForWindows(int32 cid, uint32 mask, CFArrayRef wids) -> CFArrayRef` (+1); `CGSGetActiveSpace(int32 cid) -> isize`; `CGSCopyActiveMenuBarDisplayIdentifier(int32 cid) -> CFStringRef` (+1).

| Risk | Evidence | Mitigation |
|---|---|---|

## 11. Open questions and limitations

### 11.1 Claims the verifier could not settle

- **What `NSStatusItem VisibleCC` controls.** Ice seeds it on macOS 26 with no source comment (Ice/MenuBar/ControlItem/ControlItem.swift:657-667, 697-698). All three keys are 1 on this host. A link to Control Center's menu bar allow list is a guess.
- **Whether Accessibility trust alone makes the active `CGEventTapCreateForPid` taps and cross-process posting work on 26.3**, or whether Input Monitoring is also consulted. A failed tap only logs an error (Ice/Events/EventTap.swift:133), so it would surface as a timeout. Not tested.
- **What the window server does with field 0x33 and why moves need double delivery** (session tap, then `CGEventPostToPid`) while clicks do not. The source labels the relay "Casts forbidden magic" (Ice/MenuBar/MenuBarItems/MenuBarItemManager.swift:674-675) and explains nothing more.

### 11.2 Unknowns from static and runtime work

- Why the expanded divider measures 5016 pt instead of 10,000, and whether the cap varies by display or OS build.
- Exact semantics of `Preferred Position`; the "distance from the right edge" reading is arithmetic on a few items.
- Why the item's origin changes after the Command mouse-down alone, which the first move-response wait depends on.
- Ordering rules of `CGSGetProcessMenuBarWindowList`; AudioVideoModule appeared out of x order.
- Behavior with "Displays have separate Spaces" off; the activeSpace filter would likely stop removing per-display copies.
- When windows titled `System Status Item Clone` appear; none were seen.
- Whether `kCGWindowName` on Control-Center-owned windows is readable without Screen Recording on 26.
- Why about half of off-screen per-display item copies capture as fully transparent, and which copy Ice's cache selects.
- Root cause of the 18:35:40 source-PID miss and of the hourly XPC session cancellations (messages are `<private>`).
- Whether the zero-width constraint is still found on 26.3; the shown-state divider width was never measured.
- Effective `hidesOnDeactivate` of the Ice Bar panel and whether its background drag (`isMovableByWindowBackground`) has any lasting effect.
- Whether the listen-only HID mouse tap fails without Accessibility on 26.
- Latency of the per-item sequential `sendSync` path; not measured.
- How TCC attributes the XPC service's Accessibility trust (inferred: to Ice as the responsible process). Only `TCCAccessRequest() IPC` log lines were seen.
- Whether Ice's own control items are reliably AX-attributed on 26. The AX probe skipped Ice's process to stay read-only, and the 18:35:40 log shows at least one miss.
- Whether a cached `AXExtrasMenuBar` element can hang the service: the health checks run only before the first fetch per app (MenuBarItemService/SourcePIDCache.swift:65-68), and Ice source sets no AX messaging timeout although AXSwift imports `AXUIElementSetMessagingTimeout`.
- Short Swift strings (`UseIceBar`, `Clock`, `BentoBox-0`, `com.apple.dock`, `Window Server`, `_HIHideMenuBar`) live as code immediates; the Q1 `find_small_strings.py` helper corroborated some (`VisibleCC`, `ShowIceIcon`, `UseIceBar`, `_HIHideMenuBar`, `com.apple.dock`); the others are confirmed from source only.

### 11.3 What the evidence did not cover

- **No live hide/show, move, click or Ice Bar session.** The rules forbade posting events, clicking, or changing defaults. UseIceBar is 0 on this host, so the Ice Bar panel was only seen at 0x0, off screen.
- **No event trace.** On-the-wire event order, timings and adaptive timeout values are from source only. Ice's unified log keeps only warning and error lines at the current configuration.
- **Millisecond delays** (25, 50, 100, 250 ms; 0.1 s) are confirmed in source only. The binary corroborated 10,000, the 3/0 length, the 3/1 window width, the 0x12 mask, the macOS 26 gate, the 150 ms and 25 ms move clamps, the 250 ms click timeout and the scroll thresholds.
- **arm64 only.** The x86_64 slices and Sparkle binaries were not examined.
- **No decompiler.** Ghidra, Hopper and IDA were not available to REA; string and ObjC evidence came from `strings`, `nm` and `otool`. Function names attached to addresses come from matching source, not from symbols.
- **TCC state not read.** Ice's Accessibility grant is inferred from setup having run; its Screen Recording state is unknown. The probe shell's own Screen Recording access came from its parent process chain.
- **Runtime snapshots are a point in time.** Positions and window IDs drift (about 33 pt between snapshots when the NowPlaying item disappeared).
